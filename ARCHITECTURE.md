# Round About: multiplayer architecture

**Status:** implemented (Tasks 1–16) and live at `https://round-about.chreisel.net`. This page records the design and the reasons behind it; [Deviations from the original design](#deviations-from-the-original-design) lists where the build differs. Deployment and AWS components: [INFRASTRUCTURE.md](INFRASTRUCTURE.md). **Target:** ~50 players across ~100 small-group games/month, each on their own device, often in a video call. Preserve one numbered-and-worded circle and one compact turn panel. Game rules run on the server; the stack is **Amplify Gen 2 Hosting and AppSync Events**.

## Player flow and decisions

1. `/` asks **Host** or **Join**. Host enters a nickname and creates a game in a lobby. Server generates an opaque random **SQUID**, e.g. `7K9M2Q4V8P6R`, and share URL `https://round-about.chreisel.net/s/7K9M2Q4V8P6R`. Join accepts either SQUID or URL, then asks for a unique in-session nickname. Following the URL takes the visitor directly to that join screen. No account, password or sign-in screen.
2. In the lobby, any participant (including host) can claim the single **Tipster** seat. The first claim accepted by the server wins; later claims fail and show who took it. The Tipster remains the same person for the entire game. Everyone else is a **Guesser**. Host can start only after someone has claimed Tipster and at least one other participant has joined as Guesser. Host privilege to start is independent of Tipster role. Players joining after start become Guessers and cannot claim Tipster for that game.
3. Tipster types locally and **presses Send word** within 20 seconds plus 3 seconds' grace; unsent text never becomes a clue. During guessing, **any Guesser** can click a gap once to select it for the team; all screens show that provisional selection. A second click on the **currently selected gap** by any Guesser locks it and triggers Reveal. Clicking another gap changes the team's selection instead. Guessers discuss over their existing video call; whoever makes the lock-in click decides for everyone. The Tipster cannot select or lock.
4. All connected players display the result at a shared target time after lock-in; a brief delay is acceptable. A disconnected Guesser can reconnect with their existing participant token. If someone leaves and play is broken, host creates a **new session with a new SQUID**, shares the new URL and everyone rejoins; the old session expires. No automatic role reassignment, pause, or disconnect forfeit is required.

## Recommended stack

```text
Amplify Hosting (static web UI + share-URL rewrite)
  browser ─ HTTPS ─► API Gateway HTTP API ─► Lambda game service ─► DynamoDB
          └ WSS ──► AppSync Events (per-session channel) ◄── Lambda publishes
                                                           └─ SQS delayed deadlines
                                                                  └─ timeout Lambda
```

Use **Amplify Gen 2** for Git-linked hosting, backend definitions and environment outputs. Build the static app with a small bundler (e.g. Vite + TypeScript modules); no SSR, mandatory React rewrite, Amplify UI components, or per-player AWS account is required. The app is served at `round-about.chreisel.net`. An SPA rewrite serves the entry page for `/s/{squid}`, while the browser reads the SQUID from the URL.

Define backend resources in `amplify/backend.ts`: Lambda handlers, a DynamoDB on-demand session table, AppSync Event API and namespace, SQS standard queue with dead-letter queue, and API Gateway HTTP API. **AppSync Events and HTTP API are CDK custom resources inside Amplify Gen 2**, not features produced automatically by `a.model()`; this still needs infrastructure code. Use `defineFunction` where appropriate and grant each handler only its needed table/queue/publish permissions. Develop with an Amplify sandbox; production (`main`) has its own backend, so an experimental change never resets friends' live games. Keep backend API URLs and region in generated Amplify outputs; no secrets in the frontend bundle. No VPC/NAT gateway, provisioned Lambda concurrency, SSR, chat, or always-on server planned for v1.

**Why AppSync Events instead of generated Amplify Data subscriptions:** it manages WebSocket connections and room broadcasts without maintaining API Gateway connection IDs, while the game still stores one authoritative session aggregate. Generated `a.model()` CRUD/subscriptions and client-side `observeQuery()` are a poor boundary for a secret deck and role/phase-dependent permissions: never expose raw game records or let browsers update cards/lives directly. Model subscriptions inherit mutation selection sets, and custom subscriptions have owner-authorization limitations. Use explicit server commands and a **public event channel** instead; browser **cannot publish** game events. AppSync GraphQL custom operations are a viable alternative after an auth/projection proof of concept, but should not run in parallel with a second command API.

## Identity and authorization

- SQUID: server-generated cryptographically random ~12-character Crockford Base32 code (~60 bits), collision-checked with conditional write. It is a shareable invitation, **not** an authorization credential. Do not embed the hidden number, participant credential, or answer in links.
- On host/join, game API issues a random participant ID and high-entropy participant token **without any login flow**. Store only its hash server-side; keep the token in browser `sessionStorage`, scoped by SQUID (survives refresh in that tab, not closing it; never in URL). Store the nickname in `localStorage` only as a convenience to prefill the next join form. The server records the actual nickname in session membership and sends it in snapshots; editing local storage cannot change an existing participant's name or role. Reject case-insensitive duplicate nicknames within a session. Joining from another device/browser creates a new seat unless a future explicit recovery flow is added; losing the token means rejoining with a different nickname or asking the host to release the old seat. Cap session size at 12 players (rate limiting of creates/joins is not implemented yet).
- **No Amplify Auth/Cognito or persistent user accounts in v1.** A nickname identifies a player to friends, but is not proof of identity; SQUID alone is a shareable invitation, not permission to read Tipster secrets or issue commands. The API checks the participant token, session membership, host/Tipster/Guesser rights and phase on every read/command. Only lobby members can claim Tipster; all guesses must come from a Guesser. Expire participant tokens with the session and use DynamoDB TTL for abandoned sessions. Anyone controlling an unlocked device/tab can act as that player, as with other guest-session games.
- AppSync Events channel `/games/{squid}` requires **per-session subscribe authorization** backed by the participant token (use a short-lived, room-scoped connection credential where the chosen client SDK needs one). Configure Event API connection auth and namespace `OnSubscribe` checks for membership; deny client publish in auth configuration and `OnPublish`, with only the backend IAM role permitted to publish after a commit. Do **not** use a shared browser API key, `allow.guest()`, a nickname, or a channel-name filter as the sole gate. The browser passes its participant token in the WebSocket subprotocol header; a Lambda authorizer checks it against the session on connect and subscribe. A deployed spike (Task 7) confirmed this boundary, so the API Gateway WebSocket fallback was not needed.

## State and game service

Store one private DynamoDB session item per SQUID (size capped well below 400 KB), with `version`, host and participants (nickname and token hash), one fixed `tipsterId`, `turnId`, phase, UTC deadline, sorted circle cards `{number,word}`, unused-number deck, pile count, drawn number, submitted clue, shared provisional selected gap, lives, overtime, last result, recently applied command IDs, and TTL. Separate **public projection** from private state: all participants see numbered-and-worded circle, nicknames, Tipster, shared provisional selection, lives, pile, submitted clue and phase; only Tipster gets `currentDraw` on an authorized draw response/read during clue entry and grace. No future deck, hidden number or correct gap in Guesser responses, event payloads, frontend state or logs before Reveal. Handoff hides number until Reveal. Typed-but-unsent clue stays in Tipster's browser.

Move rules out of `app.js` into a pure TypeScript reducer independent of AWS: `apply(state, command, now) → nextState + effects`. The server alone shuffles and draws numbers, validates one-word format and exact duplicates, computes correct gap including 100→0, and decides timeout, lost life and win. Semantic clue restrictions need players' judgment. Retain prototype invariants:

- Begin with 0/100, 33 and 66, each with a random distinct word. `cards` remain in ascending number order; 0 is one wrap card, not separate 0 and 100 cards.
- The 12-card pile is a **goal, not a turn limit**. Each draw consumes a pile card. Wrong guess still inserts the drawn card at its correct spot and loses a life; wrong last-card placement requires replacement draws until one is placed correctly. A 20-second clue timeout plus 3-second grace with no submitted word discards card, costs a life and restores one pile card.
- Third lost life starts Overtime. In Overtime, team has 20 seconds to **lock** a gap; a further miss or timeout loses. Correctly placing the last card wins even in Overtime.

Recommended command API: `POST /sessions` (host or restart with a fresh SQUID), `POST /sessions/{squid}/participants` (join), `GET /sessions/{squid}` (authorized snapshot), `POST /sessions/{squid}/commands` (`CLAIM_TIPSTER`, `START`, `DRAW`, `SUBMIT_CLUE`, `CHOOSE_GAP`, `LOCK_GAP`, `NEXT_TURN`). Each command carries `turnId` where applicable, unique command ID and expected `version`; reject stale phase/version (409 + fresh **caller-projected** state), deduplicate retries, and conditionally update DynamoDB by version. `CLAIM_TIPSTER` succeeds only while lobby is open and `tipsterId` is unset; simultaneous claims have one winner. In guess phase, a click on another/unselected gap commits `CHOOSE_GAP`, broadcasts the new selection and stays in guess phase; a click on the **currently** selected gap submits `LOCK_GAP` only after the client has observed/acknowledged that selection. Server checks that the chosen gap and expected version still match, then atomically grades and reveals. If another Guesser moved the selection meanwhile, return 409; client shows current selection and waits for another click. Any Guesser can issue either command, including locking a gap chosen by someone else. There is no standalone Reveal button. Client never supplies drawn number, correct answer, remaining lives or authoritative timestamp. Preserve Overtime deadline on every selection/rerender/reconnect.

## Shared reveal and short timers

1. On any committed **public** transition, the backend publishes a versioned, safe public event to `/games/{squid}`; the private `DRAW` response is never broadcast. Event API fans out to session subscribers; no connection registry in game service. `CHOOSE_GAP` broadcasts the shared provisional highlight before any lock-in; version checks prevent a stale second click from locking a different gap. Publishing is driven by the table's DynamoDB Stream, so every committed write is published (with retries and a failure queue) and the API never publishes itself; clients reconcile via authorized GET on reconnect or missed-version detection. The command response to `LOCK_GAP` is an acknowledgment **without an early result**, so the committing Guesser sees it with friends, not before them.
2. `LOCK_GAP` grades placement and stores the result, a pre-reveal public projection, and a server-set `revealAtUtc` about two seconds ahead. Broadcast the versioned result + intended reveal time. Clients buffer and display it at that time using server time from the latest API response; a late client displays immediately. A snapshot requested before reveal time returns the pre-reveal projection plus pending result and target time, so its caller also waits; after target time the snapshot returns normal post-reveal state. Reject `NEXT_TURN` until the reveal time has passed. This makes reveals near-simultaneous rather than exactly synchronous across arbitrary networks. The payload can still be inspected before display: shared timing is UX, not an anti-cheat guarantee. If that matters, broadcast only a reveal marker and publish result after target time instead.
3. Set UTC deadlines server-side. Browser countdown is visual; server validates time on commands. At 20 seconds without submitted clue, enter grace regardless of unsent text. At 23 seconds, discard if still unsent. Overtime guessers have 20 seconds to lock a gap; highlight alone does not count. Enqueue an SQS delayed message on each deadline change with SQUID + turnId + expected phase/deadline. Timeout Lambda uses conditional update and ignores duplicates/stale messages; reconcile elapsed deadlines before **every** read/command so delayed queue delivery cannot extend allowed play. Derive grace expiry from original deadline, not worker arrival. EventBridge Scheduler minute-level precision cannot drive 3-second grace. Delivery may be late by a little; broadcast any committed timeout transition and alert on dead-letter queue/latency.
4. On WebSocket reconnect, fetch authorized snapshot to catch up (AppSync subscriptions may miss messages while offline); ignore out-of-order versions. Show connection health and retry. Disconnect does not pause server timer. Reconnect recovers Tipster's private number during clue entry but cannot recover an unsent typed word. If a player leaves and play cannot continue, start a new session (`POST /sessions`) and have the team join its new URL. No automatic reassignment or timeout-based removal of absent players.

## Implementation and verification

Layout: `web/` (minimal UI, transport, clock offset), `game/` (pure reducer and tests), `amplify/` (Gen 2 definitions, handlers, event authorizer, publisher, deadline workers), `shared/` (typed commands, projections, deadline reconciliation). `game/` has no AWS imports. The original single-browser prototype was removed in issue #4.

Test sorted/wrap insertion, wrong last-card replacement, grace timing with explicit Send word, third-life Overtime, final win in Overtime, simultaneous first-come Tipster claims, joining mid-game as Guesser, two-click shared selection/lock, competing Guesser clicks and stale versions, new-session restart, replayed commands and deadline races. Add projection tests proving hidden draw/deck never reach Guessers or public events. Run a deployed dev spike with three browsers: subscribe as member, reject nonmember and browser publishing, verify selection appears on all screens, second click locks once, result displays together, refresh/reconnect catches up, no result leaks via pre-reveal GET. CI and the Amplify build both run `npm run check` (format, typecheck, tests, build); changes are verified in the sandbox before a pull request reaches production. Logs carry error names only, **never** tokens or secret numbers; alarms cover failed timeouts, deadline scheduling, event publishing, throttling and API 5xx.

## Deviations from the original design

- **Clue hand-off:** sending the word starts guessing immediately; there is no separate hand-over step.
- **Event publishing:** a DynamoDB Stream feeds a publisher Lambda instead of the game API publishing after each write with a stored pending event.
- **Deadline delivery:** a stream consumer (`deadline-scheduler`) enqueues the delayed SQS message for every saved deadline, rather than the API enqueuing it.
- **Rate limiting** of creates/joins is not implemented; only the 12-player cap is.
- **PR previews** are not used; changes are tested in a developer sandbox.
- **Restart:** the host's ↻ New game creates the replacement session via `POST /sessions` with `{ replaces }`; the old session points to the new code, refuses commands and expires after 10 minutes.

## What Amplify changes (and what it does not)

Amplify Hosting removes manual CDN/S3 deployment; AppSync Events removes manual WebSocket connection tracking and fan-out. Guest nicknames avoid account-management UI but do **not** remove per-SQUID membership checks, private Tipster views, atomic game commands or sub-minute deadlines: those remain custom code. AppSync Events and other custom backend resources are billed by their underlying AWS services; Amplify Hosting has separate hosting/build charges. At this small scale, prefer less custom runtime plumbing over optimizing cents, but validate the real per-session subscription auth in a working spike first.
